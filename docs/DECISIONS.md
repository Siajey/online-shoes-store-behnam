# DECISIONS.md — لاگ تصمیم‌ها

## چطور از این فایل استفاده کنیم

- هر تصمیم مهم (معماری، ابزار، قرارداد با بک‌اند، طراحی) یک ورودی جدید می‌گیرد.
- ورودی‌های قدیمی حذف نمی‌شوند. اگر تصمیمی عوض شد، ورودی جدید می‌نویسیم و وضعیت قدیمی را «جایگزین‌شده با D-0XX» می‌کنیم.
- وضعیت‌ها: `پیشنهادی` (هنوز تأیید نشده) | `تأییدشده` | `جایگزین‌شده`
- هر ورودی جدید داخل یک PR (یا همراه کامیتی با پیشوند `docs:`) ثبت شود.

### قالب

```
## D-0XX — عنوان کوتاه
- تاریخ:
- وضعیت:
- تصمیم:
- دلیل:
- جایگزین‌هایی که بررسی شد:
- پیامد / ریسک:
```

## D-016 — سبد خرید مهمان در مرورگر

- تاریخ: 2026-11-04
- وضعیت: تصمیم گرفته شد
- تصمیم: سبد خرید مهمان در `localStorage` (کلید `cart`، نسخه‌ی ۱) نگه داشته می‌شود و با `useSyncExternalStore` به صفحه‌ها وصل است. تب‌ها با رویداد `storage` هم‌گام می‌شوند.
- ردیف سبد: شناسه، slug، نام، قیمت، قیمت قبلی و تصویر را هنگام افزودن ذخیره می‌کند تا صفحه‌ی سبد بدون درخواست به API نمایش داده شود.
- ⚠ قیمت ذخیره‌شده فقط برای نمایش است. در مرحله‌ی پرداخت، سرور قیمت و موجودی را دوباره حساب می‌کند و فرانت به قیمت سبد اعتماد نمی‌کند.
- سقف تعداد هر کالا: ۱۰ (`MAX_QUANTITY`) تا موجودی انبار از API مشخص شود (☐).
- محتوای خراب یا دستکاری‌شده‌ی حافظه بی‌صدا نادیده گرفته می‌شود (zod).
- روی سرور و هنگام هیدریت، سبد خالی است؛ صفحه‌ی `/cart` تا خواندن حافظه اسکلت نشان می‌دهد.
- کارهای بعدی (☐): ادغام سبد مهمان با سبد حساب بعد از ورود (نیازمند API همکار)، صفحه‌ی پرداخت، علاقه‌مندی‌ها.

## D-018 — ورود و ثبت‌نام با کد پیامکی (تأیید با کد بک‌اند)

- تاریخ: 2026-11-05
- وضعیت: پیاده‌سازی شد (بر اساس شاخه‌ی feat/users-auth-sessions بک‌اند)
- ثبت‌نام جدا نیست: ورود با کد، برای شماره‌ی تازه خودش حساب می‌سازد (`POST /auth/login`، سپس `POST /auth/verify-login-otp`).
- ورود و تأیید کد CSRF نمی‌خواهند. فقط درخواست‌های تغییردهنده‌ی بعد از ورود (مثل خروج) هدر `x-csrf-token` می‌فرستند.
- توکن CSRF از پاسخ تأیید کد (`data.csrfToken`) گرفته می‌شود و در حافظه‌ی کلاینت می‌ماند.
- هدر `x-lang` دیگر فرستاده نمی‌شود: بک‌اند پیش‌فرض فارسی است و هدر سفارشی باعث preflight می‌شود که CORS فعلی بک‌اند آن را مجاز نکرده.
- ✅ CORS بک‌اند `x-csrf-token` را در `allowedHeaders` دارد (D-025).
- کد تأیید ۶ رقم است؛ در محیط توسعه همیشه `123456` (قبلاً `12345`) و در محیط واقعی تصادفی. فرانت فقط ۴ تا ۸ رقم را می‌پذیرد.
- فرانت روی پورت ۳۰۰۱ اجرا می‌شود (`pnpm dev`)، چون CORS بک‌اند فقط این origin را مجاز می‌داند.
- بازیابی رمز با ایمیل (D-012) در این شاخه‌ی بک‌اند نیست؛ بعداً.

## D-021 — پروفایل و آدرس‌ها (صفحه‌ی حساب)

- **تصمیم:** `/account` فرم نام و نام خانوادگی دارد (`PATCH /users/me`) و `/account/addresses` مدیریت آدرس‌ها (`/users/me/addresses`). بین این دو زبانه‌ی `AccountTabs` است.
- **منبع حقیقت سرور است:** بعد از هر تغییر (افزودن، ویرایش، پیش‌فرض، حذف) فهرست دوباره خوانده می‌شود؛ حالت محلی جداگانه نگه نمی‌داریم.
- **سقف ۲ آدرس:** وقتی ۲ آدرس هست دکمه‌ی افزودن نمایش داده نمی‌شود؛ اگر سرور هم ۴۰۹ بدهد، پیام فارسی بک‌اند در فرم دیده می‌شود.
- **کلاینت API:** پاسخ ۲۰۴ بدون بدنه (حذف آدرس) موفقیت است؛ ۲۰۰ بدون بدنه همچنان `INVALID_RESPONSE`.
- **اعتبارسنجی:** نام‌ها ≤۲۰ حرف و الزامی؛ آدرس: همه‌ی فیلدها الزامی، ≤۱۰۰ حرف، کدپستی ۱۰ رقم (ارقام فارسی پذیرفته).
- **✅ وابستگی بک‌اند حل شد:** `x-csrf-token` در CORS مجاز شد و باگ کوکی CSRF هم رفع شد (D-025).

## D-022 — صفحه‌ی تسویه‌ی حساب (بدون ثبت سفارش)

- **تصمیم:** `/checkout` سبد (از حافظه‌ی مرورگر) و آدرس تحویل (از `/users/me/addresses`) را نشان می‌دهد. مهمان به `/login?next=/checkout` می‌رود. صفحه `noindex` است. دکمه‌ی «ادامه‌ی خرید» در سبد حالا لینک به همین صفحه است.
- **انتخاب آدرس:** پیش‌فرض، وگرنه اولین؛ اگر آدرس انتخاب‌شده حذف شد به پیش‌فرض برمی‌گردد (`resolveSelectedAddressId`).
- **ثبت سفارش غیرفعال است:** API سفارش و پرداخت در بک‌اند نیست. هیچ سفارش ساختگی ساخته نمی‌شود (D-014). ☐ بعد از آماده شدن API: دکمه سفارش را ثبت کند، هزینه‌ی ارسال از سرور بیاید، و قیمت‌ها قبل از ثبت دوباره از سرور تأیید شوند (قیمت سبد محلی قابل اعتماد نیست).

## D-023 — خطا، SEO و صفحه‌ی سفارش‌ها

- **خطا:** `app/(site)/error.tsx` با `ErrorView`؛ جزئیات فنی خطا هرگز به کاربر نشان داده نمی‌شود. ☐ گزارش به Sentry بعداً.
- **SEO:** `robots.ts` و `sitemap.ts` از `lib/seo.ts` ساخته می‌شوند. آدرس سایت از `NEXT_PUBLIC_SITE_URL` (پیش‌فرض محلی `http://localhost:3001`). مسیرهای خصوصی (حساب، سبد، تسویه، علاقه‌مندی، ورود، dev) بسته‌اند. ☐ صفحه‌های محصول بعد از API به sitemap اضافه شوند.
- **سفارش‌ها:** `/account/orders` جای‌نگهدار صادقانه است (لینک منوی موبایل قبلاً به ۴۰۴ می‌رفت). زبانه‌ی «سفارش‌ها» به `AccountTabs` اضافه شد. ☐ فهرست واقعی بعد از API سفارش.

## D-024 — صفحه‌های نتیجه‌ی پرداخت و صفحه‌های اطلاعاتی بیشتر

- **نتیجه‌ی پرداخت:** `/checkout/success` و `/checkout/failed` فقط قالب‌اند (noindex) و داده‌ی ساختگی ندارند. ☐ با API پرداخت، شماره‌ی سفارش و وضعیت واقعی از سرور بیاید و بازگشت از درگاه روی همین مسیرها فرود بیاید.
- **پرداخت فقط آنلاین است** و در قوانین هم همین آمده؛ گزینه‌ی «پرداخت در محل» وجود ندارد.
- **صفحه‌های جدید:** درباره‌ی ما، تماس با ما (از `siteConfig.contact`)، قوانین و مقررات، حریم خصوصی. متن‌های حقوقی پیش‌نویس‌اند و با یادداشت در صفحه مشخص شده‌اند. ☐ مالک بازبینی کند. لینک‌ها به فوتر (گروه پشتیبانی) اضافه شد.
- **sitemap:** این صفحه‌ها باید به `PUBLIC_PATHS` در `lib/seo.ts` اضافه شوند (اگر PR کیفیت merge شده باشد).

## D-025 — بستن مسئله‌ی CSRF و وضعیت بک‌اند

- **باگ بک‌اند:** `generateCsrfCookie` در رابط سه پارامتر داشت ولی پیاده‌سازی دو تا؛ پس `POST /auth/csrf-token` توکن را به‌جای secret در کوکی `csrf_secret` می‌نوشت و هر درخواست بعد از رفرش ۴۰۳ می‌داد. اصلاح: دو پارامتر در رابط و usecase، و مقدار پیش‌فرض `'csrf'` برای `CSRF_TOKEN_SECRET` در ورود. CORS هم `x-csrf-token` را مجاز کرد.
- **تأیید:** ذخیره‌ی پروفایل و آدرس، خروج و رفرش صفحه در مرورگر بدون خطا کار می‌کنند.
- **کوکی‌ها:** هر سه کوکی (`access_token`، `refresh_token`، `csrf_secret`) `SameSite=Lax` و بدون `Domain` هستند. در production فرانت و API باید هم‌سایت (same-site) باشند و HTTPS لازم است.
- **محصولات:** ماژول محصول فقط در PR شماره‌ی ۱۰ بک‌اند (merge نشده، فقط لایه‌ی دامنه و کاربردی، بدون مسیر HTTP) است. هر محصول چند «تنوع» با `sku`، `price`، `stock` و `attributes` (نام و مقدار، مثل سایز و رنگ) دارد؛ فیلتر بر اساس دسته، برند، بازه‌ی قیمت، موجودی و ویژگی‌ها و صفحه‌بندی با `nextCursor`. ☐ بعد از آمدن کنترلرها، لایه‌ی API و صفحه‌ی محصول (سایز و رنگ) وصل شود.

## D-026 — صفحه‌ی خوش‌آمدگویی موبایل، جمله‌ی قوانین در ورود، لینک «درباره‌ی ما»

- **خوش‌آمدگویی:** `/welcome` اولین صفحه‌ی طرح موبایل است (نام برند، تصویر کفش، عنوان، توضیح، دکمه‌ی «شروع کنید»). خارج از چیدمان فروشگاه (بدون هدر و فوتر) و `noindex`.
- **نمایش خودکار:** `WelcomeGate` در صفحه‌ی اصلی، فقط برای موبایل (زیر ۱۰۲۴ پیکسل) و فقط بار اول، به `/welcome` هدایت می‌کند. «دیده شد» با کلید `welcome-seen` در `localStorage` (خواندن و نوشتن امن) ثبت می‌شود. ☐ چون هدایت سمت مرورگر است، لحظه‌ای صفحه‌ی اصلی دیده می‌شود؛ اگر آزاردهنده بود با middleware و کوکی جایگزین شود.
- **نقطه‌های صفحه‌نما:** طرح سه نقطه دارد ولی فقط یک اسلاید طراحی شده؛ فعلاً حذف شدند. ☐ اگر اسلاید دوم و سوم طراحی شد، اضافه شوند.
- **ورود:** زیر دکمه‌ی «دریافت کد» جمله‌ی «با ورود، قوانین و حریم خصوصی کفش بهنام را می‌پذیرم.» با لینک به `/terms` و `/privacy` آمد (طبق طرح).
- **هدر:** «درباره‌ی ما» به ناوبری اصلی اضافه شد (طبق طرح).
